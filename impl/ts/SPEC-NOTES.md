# 仮実装で見つかった仕様の論点

仕様書 v0.4 を実装して気づいた、曖昧な点や決めておきたい点です。仮実装での暫定の扱いも書いています。仕様を直すときは、この一覧を元に v0.5.0 へ反映します。

## 確認できたこと

- §4.2 の例 `LP(ascii("ab"), ε) = 00000002 6162 00000000` は実装と一致した。
- §10.3 の例（`hashInput` 102バイト、`operationId = 5f1a2b8b…b461`）は実装、`node:crypto`、`sha256sum` のいずれでも一致した。
- §8.2 の `len(MsgHeader) = 115 + len(context)` は実装と一致した。
- ECDH の共有秘密が `0x00` で始まる場合も、Web Crypto API の `deriveBits(…, 256)` は32バイトを返す（`ecdh.json` に例を収録）。

## 論点

### 1. テストベクターの異常系のエラーコード（§16）

§16 は異常系に `"expectedError": "<code>"` を持たせるとしているが、`base64url`、`ecdh`、`utf8`、`challenge` などの低レベルの検査で使うコードは定義されていない。
**暫定**: `invalid_base64url`、`invalid_public_key`、`invalid_utf8`、`bad_request` を使った。
**提案**: ベクター用のコードの一覧を §16 に載せる。ワイヤ上のエラー（§12）とは別物であることも書く。

### 2. テストベクターのJSONでの表し方（§16）

`ε` の表し方、文字列の入力（TAの `content` など）を16進にするか文字列にするかが決まっていない。
**暫定**: `ε` は空文字列 `""`。テキストはJSON文字列、バイト列は小文字の16進。

### 3. WebAuthn Challenge と mode の組み合わせ（§5.5）

「mode=0x01 と `ta` の組み合わせは拒否する」とあるが、Challenge の入力には mode が含まれないため、Challenge の計算だけでは判定できない。
**暫定**: 儀式の種類（`kx` / `kr` / `ta` / `ta+kr`）を引数に取り、必要なフィールドの有無を検査する。`th` を正しい mode で計算したかは呼び出し側の責任。
**提案**: 「儀式の種類はエンドポイントで決まり、それに応じた mode で `th` を計算する」と明記する。

### 4. `u64` の範囲（§4.1、§4.8）

時刻は `u64` だが、JSON では 2⁵³ 以上の整数を拒否する。
**暫定**: `u64` の値を 2⁵³−1 以下に制限し、ワイヤ上でそれを超える値は `bad_request` とした。
**提案**: `u64` で表す値（時刻）は 2⁵³−1 以下と明記する。

### 5. ETのクエリに使える文字（§11.2）

「生のクエリ文字列」とあるだけで、使える文字が決まっていない。
**暫定**: RFC 3986 の `query`（pchar と `/`、`?`）に限り、パーセントエンコードは大文字の16進とした。

### 6. ETのエラーコード（§11.6、§12.4）

- クエリの違反に対応するコードがない。**暫定**: `invalid_path`。
- `EtRequest` 自体の形式不正（LPの不正、ラベルの不一致など）がどのコードか書かれていない。**暫定**: `invalid_request`（§12.4「平文の形式不正」）。

### 7. ETのヘッダー（§11.4）

- 「ヘッダー全体は8KiB以下」が何を数えるか。**暫定**: 名前と値のバイト数の合計（LPの長さは含めない）。
- 同じ名前のヘッダーが複数ある場合の扱い。**暫定**: 拒否する。
- `location` の「相対パスのみ」。**暫定**: `/` で始まり `//` で始まらないものだけ受理する。

### 8. `/wake/` への転送禁止（§11.3）

**暫定**: `/wake/` で始まるパスを拒否する。`/wake` そのものは登録済みルートとの完全一致で判定されるため、規則としては拒否していない。
