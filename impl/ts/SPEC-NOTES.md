# 仮実装で見つかった仕様の論点

仕様書を実装して気づいた、曖昧な点や決めておきたい点の記録です。

## v0.5 で仕様に反映したもの

v0.4 の仮実装（M1）とレビューで見つかった論点は、v0.5 の仕様に反映しました。変更点の一覧は[仕様書 §0](../../spec/wake-protocol.md#0-v04からの主な変更)を参照してください。

| 論点 | 反映先 |
|---|---|
| TA文面の禁止文字をCc制御文字（LFを含む）に絞り、他の特殊文字は承認画面で可視化する | §10.4、§10.11 |
| 複数行の文面は `\n`（2文字）で表し、表示形式を切り替えても値は変えない | §10.3、§10.4、§10.11、§10.12 |
| ETは通常のHTTP要求・応答を運び、`/wake/` への転送禁止とルート照合はディスパッチ側の責任 | §11.3、§11.5 |

## M2 で見つかった論点

KX と SM をブラウザと Node のサーバーで動かして（M2）、決める必要があった点です。仮実装での扱いを書いています。仕様に反映したものは、その旨を書いています。それ以外は、仕様に反映するかは未定です。

| 論点 | 仕様の箇所 | 仮実装での扱い |
|---|---|---|
| credential の公開鍵の形式 | §6.5 | §6.5 のインターフェースは「参考」なので、COSE_Key ではなく SPKI（ブラウザの `getPublicKey()` の値）を保存する。CBOR の解析を持ち込まずに済む。対応するアルゴリズムは ES256（−7）だけ |
| 署名カウンターの更新と原子性 | §6.4、§7.5 (c) | credential ストアは実装者のもので、交換・セッションのストアと同じ原子的操作には入れられないことがある。BE が0の credential では、受信値が保存値より大きいとき、検証に使った保存値を条件にした条件付き更新（`compareAndSetSignCount`）を**ログインの確定より前に**行い、失敗したら、§7.6 の再送応答を返せればそれを返す。返せず交換がまだ PENDING なら `retry`（同じ本文の並行要求が、勝ったのにまだ確定していない場合がある。クライアントが同じ本文を再送すれば、再送応答を受け取れる）、それ以外は `auth_failed`。どちらも交換状態は変えない。複製された credential が同じ次の値で同時にログインしても、片方しか通らない。確定があとで失敗しても、カウンターが進むだけなので安全側である。BE が1の credential と、保存値・受信値がともに0の場合は、確定の直後に `max(保存値, 受信値)` で更新する。確定のあとで更新に失敗した場合に備え、未適用の更新を交換に記録し、§7.6 の再送で適用し直す。異常の通知は1回だけ行う |
| カウンターの判定に使う BE | §6.4 | 受信した authenticatorData の BE フラグではなく、登録時に保存した `backupEligible` を使う。受信値で拒否の規則を緩められないようにするため。「記録・通知」は確定後に呼ぶコールバックにした |
| `crossOrigin` 以外の clientData の項目 | §6.2 手順3 | `topOrigin` があれば拒否する（`crossOrigin` が `true` の場合に付く項目のため）。`crossOrigin` は、ないか `false` のときだけ受理する |
| authenticatorData の拡張 | §6.2 | AT フラグが立っていれば拒否する。ED フラグが立っている場合、末尾の拡張データは解析せずに受理する（署名の対象には含まれる）。ただし拡張データがない（長さが37バイトちょうど）ものは拒否する。ED が立っていなければ長さは37バイトちょうど。BE なしで BS が立っているものは拒否する |
| `userHandle` が省略された場合 | §6.2 手順8 | discoverable でも省略を許す。ユーザーは credential ID で引いた credential から決まるため |
| 偽の credential ID の作り方 | §6.6 | `HMAC(サーバー秘密, LP("wake-server fake-credential", username, u32(i), u32(block)))` を必要な長さまで連結し、設定した長さ（16〜64バイト、既定32）で、設定した件数（1〜16、既定1）返す。実在ユーザーでも同じ HMAC の計算をし、有効な credential が設定した件数より少なければ、偽の ID で設定した件数まで埋める。応答時間の調整は実装者に残る |
| §6.6 の「同じ件数分布」の限界 | §6.6 | 偽の ID で件数を埋めても、設定した件数より多くの credential を持つユーザーは件数から、また実在の credential ID の長さ（認証器ごとに16〜64バイトなどと異なる）は長さの分布から見分けられる。件数の設定はユーザーが持てる credential の最大数に合わせるとよいが、ID の長さまで含めると、仕様の「実在ユーザーと区別できない応答」は完全には満たせない。username 方式を使うなら、この限界を前提にするか、discoverable 方式を勧めることになる |
| `allowCredentials` の `transports` | §6.1、§6.6 | §6.1 の例には `transports` があるが、本物の credential は保存した値、偽の credential は固定値になり、1回の応答で区別できてしまう。仮実装では、本物にも偽物にも `transports` を付けない |
| 未知のユーザー名でログインしたとき | §6.6 | 偽の credential ID は認証器に存在しないので、正しく動く認証器では `navigator.credentials.get()` がブラウザ側で失敗し（`NotAllowedError`）、サーバーには何も届かない。ユーザーに何を見せるかは仕様に書かれていない。デモでは、その失敗をそのまま表示する |
| ユーザー名の長さ | §7.2 | 規定がないので、1〜256（UTF-16 の単位）とした |
| `/auth/*` の本文の上限 | §12.5 | 規定がないので64KiBとし、超過は `bad_request`（§12.5 に `too_large` がないため） |
| `/auth/complete` の形式不正の境界 | §7.5、§7.8 | 外側の項目（`exchangeId`、`clientFinished` の長さ、`assertion` がオブジェクトか）の不正は `bad_request`。assertion の中身の不正は WebAuthn 検証の失敗として `auth_failed` |
| 暗号化されたエラーの HTTP ステータス | §12.4 | 規定がないので200。外側のエラーとは Content-Type（`application/wake` と `application/json`）で区別できる |
| 復号前の予期しない障害 | §12.3 | 外側の `retry`（503）。復号した後の予期しない例外は、暗号化した `internal` |
| `wake/session`・`wake/logout` の要求と、ログアウトの応答の平文 | §12.2、§8.9 | 規定がないので、要求はどちらも `{}`（未知の項目は無視）、ログアウトの応答は `{}` |
| 期限の境界 | §7.5、§8.1、§8.5、§8.6 | 交換は `now ≥ expiresAt` で期限切れ（§7.5 の擬似コードどおり）。セッションの絶対有効期限・上限・無操作期限も同じく「その時刻になったら期限切れ」とした。鮮度は `\|serverNow − issuedAt\| = W` まで受理し、旧世代は `now = prev_valid_until` まで受理する |
| 無操作期限を延ばす要求 | §8.10 | 復号でき、鮮度の検査（§8.5）に通った要求だけを活動として数える。`stale_request` になった要求では `last_activity_at` を更新しない |
| 暗号化回数の数え方 | §8.7 | サーバーは、復号できた要求ごとに c2s と s2c の回数を鍵世代ごとに数え、上限（既定2²⁸）に達したら `reauth`、2²⁴ 回で `rekeyRecommended` を `true` にする。クライアントも c2s を数え、上限で再ログインを求める。M2 の保存はメモリだけなので、ページの再読み込みで鍵ごと消える |
| クライアントが1回の復号失敗で鍵を消すか | §12.3 | 応答の復号失敗は `reauth` のエラーにするが、鍵は消さない。応答は偽装されうるので、1回で消すと妨害に使える。外側の `reauth` を受けたとき、期限や回数の上限に達したときは消す |
| ログアウトの通信失敗 | §8.9 手順4 | 応答の有無にかかわらず鍵を消し、通信の失敗は呼び出し側に返さない。サーバーが返したエラーは返す |
| `/auth/complete` の再送の期限 | §7.2、§7.7 | `expiresAt` はサーバーの時刻だが、`/auth/complete` の前はクライアントに時刻の offset がない。端末の時計が TTL 以上ずれていると、1回も送らずに失敗していた。**§7.2 の応答に `serverTime` を追加して解消した（v0.5）**。クライアントは `t₀ + (expiresAt − serverTime)` を期限にし、最初の1回は必ず送る |
| `/auth/complete` の応答の読み取り失敗 | §7.7 手順5、§7.8 | 本文の途中で切れた応答と、JSON でない 5xx（502、504 など）は、ネットワークエラーと同じく同じ本文を再送する。JSON の `{"error":"retry"}` も再送する。それ以外の JSON のエラーは確定する |
| `rate_limited` の `Retry-After` | §12.3、§12.5 | §12.3 は「`Retry-After` に従う」とするが、値の決め方はない。仮実装は設定値（既定1秒）を付ける |
| `/auth/*`・`/wake/up` への POST 以外の要求 | §12.1、§12.3 | 405（`Allow: POST`）と、本文 `bad_request` を返す。§12.3・§12.5 の表では `bad_request` は400だが、HTTP の意味に合わせて405にした |
| 終了したセッションの保持 | §8.1、付録A | 失効・期限切れのセッションは、鍵をすぐ消し、記録は保持期間（既定10分）のあとで消す。メモリのストアは、交換を作るときに一定間隔で期限切れの交換とセッションを掃除する |
| クライアントの予約 context | §8.8 | 汎用の `request()` では、`wake/` と `wake-` で始まる context を送らない（`bad_request`）。`wake/logout` を通すと、サーバーだけ失効してローカルの鍵が残るため |

## M3 で見つかった論点

KR・TA・ET を実装して（M3）、決める必要があった点です。書き方は M2 の節と同じです。

| 論点 | 仕様の箇所 | 仮実装での扱い |
|---|---|---|
| KR の暗号化されたエラー | §9.4、§12.4 | 交換がない・別のセッションのもの・承認試行に結び付いたもの・`kind` が違うものは `not_found`。`PENDING` でない、または期限切れは `expired`。世代が進んでいれば交換を `SUPERSEDED` にして `conflict`。WebAuthn と `clientFinished` の失敗は `webauthn_failed`（交換は変えない） |
| `wake/kr/start` の期限 | §9.2、§7.7 | §9.2 の応答には `serverTime` がないが、暗号化通信の中ではクライアントが認証済みの offset（§8.5）を持っているので、`expiresAt − offset` で端末の時刻に換算できる。§7.2 のように `serverTime` を足す必要はない |
| KR の確定後に credential が停止されていた場合 | §6.5、§9.4 | KX と同じく、確定のあとで credential を読み直し、停止・削除されていればセッションを失効させる。KR では応答を外側の `reauth` にする（セッションがもう使えないため） |
| 署名カウンターの競合（KR・TA） | §6.4 | KX と同じ規則。BE が0の credential は確定前に条件付き更新を行う。負けた側は、再送応答を返せればそれを返し、交換や承認試行がまだ `PENDING` なら外側の `retry`、それ以外は `webauthn_failed` |
| TA+KR の `th` の `prevTh` | §10.7、§10.8 | §10.7 は `prevTh = session.cur_th` で計算するとしているが、それでは承認までの間に通常の KR が先に確定したとき、署名の検証自体が失敗し、TA の承認まで失敗する。§10.8 の「TA と KR を独立に判定する」を満たすため、交換の作成時に保存した `prevTh` と `target_epoch` で `th` を計算し、確定の条件で「`prevTh` が今のセッションの `th` と等しく、世代が current + 1 であること」を確かめる。食い違えば `kr.result = conflict` で、TA は承認される |
| `already_decided`・`expired` の返し方 | §10.6、§12.4 | 承認試行そのものの問題（ない、別のセッション、期限切れ）は暗号化されたエラー。`wake/ta/challenge` で Operation が確定済み・期限切れのときもエラー。`wake/ta/approve`・`wake/ta/reject` での Operation の結果は、応答本文の `ta.result`・`result` で返す |
| 有効な承認試行の上限を超えたとき | §10.6、§13 | §9.2 の KR 交換と同じく、最も古い承認試行を `EXPIRED` にしてから新しいものを作る |
| TA+KR の交換と §9.2 の上限 | §9.2、§10.6 | 承認試行に結び付いた KR 交換も、セッションごとの PENDING な KR 交換の上限（既定3件）に数え、超えたら最も古いものから `SUPERSEDED` にする |
| 承認と credential の停止の競合 | §6.5、§10.7 | 承認を確定する直前に credential を読み直し、active でなければセッションを失効させて `reauth` にする（Operation は変えない）。読み直しから確定までの短い間に停止された場合は、承認が確定しうる。アプリは承認結果を使うとき、`decidedByCredentialId` の credential の状態も確かめること |
| 消費済みの承認試行の再送 | §10.7 | 保存した結果を返す前に、セッションと credential を確かめ直す。その承認試行で承認を確定した場合は `decidedByCredentialId` の credential も確かめ、停止・削除されていれば失効させて `reauth` にする（Operation は APPROVED のまま。確定した時点では有効だったため） |
| `rekey: true` の承認試行に `kr: null` で承認したとき | §10.7 | 通常の TA として受け付け、結び付いていた KR 交換を `SUPERSEDED` にする |
| TA+KR の KR 交換の期限 | §10.6、§13 | 結び付いた KR 交換の期限は交換の TTL、承認試行の期限は承認試行の TTL で、別々に判定する。KR 側だけが先に切れた場合は `kr.result = expired` で、TA は承認される |
| 取消の記録 | §10.9、§10.10 | 確定した主体を `server` として記録する |
| `createOperation` の入力の不正 | §10.2 | `content` の違反は `invalid_content`。`approverUserId`（1〜256バイトの正しい UTF-8）と `expiresAt` の違反は、§12 に該当するコードがないので `invalid_request` |
| 認否記録の公開鍵 | §10.10、付録C | 付録C は COSE_Key だが、仮実装は SPKI を保存しているので、`credentialPublicKey` は SPKI の Base64url にする。認否記録には確定時点の公開鍵も保存し、あとで credential が変わっても検証できるようにする。core の `verifyApprovalBundle` が付録C の手順1〜5で検証する |
| 承認画面の表示 | §10.11 手順5 | `content` と Nonce 行の間の本当の改行は改行の印で示す。`\n`（バックスラッシュと `n`）は左から順に2文字ずつ組にし、「改行として表示」を選んでも文字列は変えない。書式文字、異体字セレクター、私用領域、非文字、結合文字、U+0020 以外の空白を、コードポイントの印で可視化する |
| 承認の応答が読めなかったとき（TA+KR） | §10.8、§9.6 | KR が確定したかどうか分からないので、クライアントはセッションを捨てて再ログインを求める。`epoch_retired` から新しい世代に回復できた場合は、同じ `wake/ta/approve` の平文を新しい世代で送り直し、サーバーが保存した結果（消費済みの承認試行の結果）を受け取る。Operation の状態から結果を推測しない |
| KR の完了を送ったあと、期限まで結果が分からないとき | §9.6 | 世代を保存できないメモリだけのクライアントでは、旧世代を持ち続けても猶予期間のあとは `epoch_retired` が続くだけなので、`expired` を返してセッションを捨てる |
| 今の世代への外側の `epoch_retired` | §12.3 | §12.3 は「最新世代を読み込み、新しい `requestId` で再送」とするが、メモリだけのクライアントには読み込める世代がほかにないので、`reauth` として扱いセッションを捨てる。旧世代で送った要求への `epoch_retired` はそのまま返す |
| ET での §8.3 のエラー | §8.3、§11.6 | `stale_request` と `invalid_context` は、ほかの context と同じ平文の JSON `{"error":{"code"}}` で返す。§11.6 のルーティングのエラーは `EtResponse` で返す。`EtResponse` は u32 の長さで始まり `{` では始まらないので、クライアントは区別できる |
| ET のハンドラーの失敗 | §11.6 | ハンドラーが例外を投げた場合や、不正な応答（status・ヘッダー・本文の上限）を返した場合は、500 の `EtResponse`（`{"error":{"code":"internal"}}`）を返す。§11.6 の表に該当する行がない。例外のメッセージは外に出さない |
| ET の認証情報の `epoch` | §11.5 | 要求の鍵世代を渡す（猶予期間中は旧世代のことがある）。`authTime` と `credentialId` も、その鍵世代を確立した認証のもの（KX または KR の時刻と credential）を渡す。旧世代の要求に新しい世代の値を渡さない |
| ET の本文の上限と `maxPlaintext` | §8.7、§11.2 | ルートを登録した場合だけ、`maxPlaintext` が設定した本文の上限での最悪の `EtRequest` の長さ以上であることを設定の検査で求める |
| `/wake/up` と `/wake/transport` の context | §11.1、§12.1 | `/wake/transport` は `wake-et` だけ、`/wake/up` は `wake-et` 以外だけを受け付け、どちらも違えば暗号化した `invalid_context` |

## 確認できたこと（v0.4 時点）

- §4.2 の例 `LP(ascii("ab"), ε) = 00000002 6162 00000000` は実装と一致した。
- v0.4 の §10.3 の例（`hashInput` 102バイト、`operationId = 5f1a2b8b…b461`）は、実装、`node:crypto`、`sha256sum` のいずれでも一致した。
- §8.2 の `len(MsgHeader) = 115 + len(context)` は実装と一致した。
- ECDH の共有秘密が `0x00` で始まる場合も、Web Crypto API の `deriveBits(…, 256)` は32バイトを返す（`ecdh.json` に例を収録）。
