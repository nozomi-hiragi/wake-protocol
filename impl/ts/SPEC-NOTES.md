# 仮実装で見つかった仕様の論点

仕様書 v0.4 を実装して気づいた、曖昧な点や決めておきたい点です。仮実装は現時点では v0.4 の記述に従い、ここに書いた暫定の扱いで動いています。
「決定した方針」は PR #2 のレビューで確認したもので、仕様と実装を同じ変更でそろえて反映します（v0.5.0 の候補）。

## 確認できたこと

- §4.2 の例 `LP(ascii("ab"), ε) = 00000002 6162 00000000` は実装と一致した。
- §10.3 の例（`hashInput` 102バイト、`operationId = 5f1a2b8b…b461`）は実装、`node:crypto`、`sha256sum` のいずれでも一致した。
- §8.2 の `len(MsgHeader) = 115 + len(context)` は実装と一致した。
- ECDH の共有秘密が `0x00` で始まる場合も、Web Crypto API の `deriveBits(…, 256)` は32バイトを返す（`ecdh.json` に例を収録）。

## 決定した方針（仕様の変更が必要）

### A. ETは通常のHTTP通信を運ぶ補助に留める（§11.3、§11.4）

Request / Response の内容を理由に、WAKE 独自のポリシーで制限しない。

- `/wake/` で始まるパスの禁止や、登録済みルートとの照合は、実際に振り分けるアプリ側の責任とする。
- クエリは通常の Web の URL 処理に合わせ、パーセントエンコードの大文字限定は外す。
- 同じ名前のヘッダーは一律に拒否せず、HTTP のフィールドごとの規則に合わせる。
- パス・クエリ・ヘッダー・本文のサイズ上限は、内容の制限とは別のものとして残す。
- `location` の「相対パスのみ」は維持する。内容に関与しない方針との関係と、仕様上の置き場所は修正前に整理する。「相対パス」を `/` で始まるもの（`//` で始まるものを除く）と解釈してよいかも明記する。

### B. TA文面の禁止文字を制御文字（Cc）に絞る（§10.4）

- 一般カテゴリ Cc の制御文字を禁止する。**LF も例外なく禁止**する（文面は1行になる）。
- それ以外の透明な文字・特殊な文字は一律に拒否せず、プレビューで位置とコードポイントを目立つ形で示す。絵文字は許可する。
- 不正な UTF-16 / UTF-8 の拒否、長さなどの形式の検査は維持する。
- 従来の禁止一覧からの変更になるため、仕様、`ta-profile` のテストベクター、§10.3 の例（改行を含む）も合わせて直す。

### C. プレビューの要件（今後のUI）

- 文字としての `\n`（バックスラッシュと n）の表示と、改行としての表示を切り替えられるようにする。
- 透明な文字・特殊な文字を可視化する。方向制御文字が、可視化のマーカー自体を並べ替えないようにする。
- 表示の切り替えで、元の `content`、`hashInput`、`operationId` は変わらない。

### D. テストベクターの書き方（§16）

- §16 に、テストベクター用の `expectedError` コードの一覧を定義する。§12 の通信上のエラーとは別物であることを明記する。
  現在使っているコード: `invalid_base64url`、`invalid_public_key`、`invalid_utf8`、`invalid_content`、`bad_request`、`reauth`、ET の `invalid_method` / `invalid_path` / `invalid_header` / `invalid_request`。
- データの表し方は現状を維持する: バイト列は小文字の16進文字列、空のバイト列（`ε`）は空文字列、テキストは JSON 文字列。

### E. ETのエラーコードの対応（§11.6、§12.4）

- クエリの違反（上限超過を含む）は `invalid_path` とする。
- `EtRequest` / `EtResponse` 自体の形式不正（LP の不正、ラベルの不一致など）は `invalid_request`（§12.4「平文の形式不正」）とする。

## 未決定の論点

### 1. WebAuthn Challenge と mode の組み合わせ（§5.5）

「mode=0x01 と `ta` の組み合わせは拒否する」とあるが、Challenge の入力には mode が含まれないため、Challenge の計算だけでは判定できない。
**仮実装**: Transcript ハッシュを mode ごとに別の型にし、儀式ごとの生成関数（KX / KR / TA / TA+KR）が受け取る型で組み合わせを制限している。
**提案**: 「儀式の種類はエンドポイントで決まり、それに応じた mode で `th` を計算する」と明記する。

### 2. 時刻の範囲（§4.1、§4.8）

`u64` 自体は 0〜2⁶⁴−1 だが、時刻は JSON にも載るため 2⁵³ 以上を扱えない。
**仮実装**: `u64` の符号化は全範囲を扱い、時刻として使う所（`issuedAt`、`serverTime`、`absoluteExpiresAt`）で 2⁵³−1 以下に制限している。
**提案**: 時刻は 2⁵³−1 以下と明記する。

### 3. ヘッダー全体の8KiB（§11.4）

何を数えるかが書かれていない。**仮実装**: 名前と値のバイト数の合計（LP の長さは含めない）。
